# アクセス状況の確認(clash-royale-api)

このサイトはGPTBot・ClaudeBot等のAIクローラーと、Chromeを偽装した高度なスキャナーからの
トラフィックが大半を占める(2026-09-20時点で全体の99%以上)。「アクセスが少ない」と早合点したり、
逆にスキャナーを実訪問者と誤カウントしたりしないよう、必ず以下の手順で機械的な除外を通してから報告する。

## 手順

1. `scripts/check-access.sh`をBashツールで実行する(引数は日本時間の日付`YYYY-MM-DD`。省略時は今日。その日の日本時間0:00〜24:00を集計する)。
   ```
   bash "C:\dev\clash-royale-api\.claude\skills\access-check\scripts\check-access.sh"
   ```
   **複数の日付を集計するときも、1本ずつ順番に実行する**(同時に走らせない)。VM側の一時ファイル(`/tmp/access-check-*`)が共通なので、並行すると互いに上書きし、後半の数字が別の日のものになる(2026-10-23に今日分の出力が10/22の中身になった)。
   このスクリプトはVMにSSHし、以下をまとめて行う。
   - 日次集計スクリプト(`/usr/local/bin/clash-royale-access-stats.sh`、UA文字列ベースの簡易ボット除外)を最新の状態に再実行
   - それに加えて`references/known_noise.md`に載っている「UAは本物のブラウザに見えるが実は人間ではない」IP(既知のスキャナー・ユーザー本人の開発用IP)も除外
   - ページ別の内訳(除外前、参考)、X(Twitter)経由のリファラの有無を出力
   - **`?from=`付きのアクセスの集計**(2026-09-21追加)。X投稿には`?from=x`を付けたURLを載せている(`archive/進捗ログ_2026-09.md`のフェーズ1.55)。**リファラが付かない流入でもこれで数えられる**ため、宣伝の効果測定はこの数字を見る。他媒体に出すときは`?from=reddit`のように変える運用。ページのURLで数えた件数はクローラーも混ざるので参考にとどめ、人の流入はビーコンの節の「流入元タグ別」(ビーコンに載る`from=`を、データセンター由来を除いて数えた件数と人数)で見る(2026-10-23から)
   - 逆引き(rDNS)は、ビーコンの送信元と検索エンジンから来たIPだけを並列で引く。以前は全IPを引いて「人間候補」(機械的な除外にかからなかったIP)を出していたが、住宅プロキシ経由のクローラーが大半で人の数を表さず、4,000IPで30分以上かかっていたので2026-10-23にやめた(ユーザーが決定)。今は1日分で5分ほど
   - **検索エンジン経由の訪問**(2026-10-04追加、フェーズ1.118)。リファラがGoogle・Bing・DuckDuckGo等のページ表示を1件ずつ出し、同じIPからビーコンが来ていれば「ビーコンあり」と付ける。最後に「実訪問(データセンター以外で、ビーコンあり)」の人数と開いたページ数を出す。検索対策(カード画面のタイトル・説明文、canonicalなど)の効果はこの数字で測る。Googleの先読み(逆引きが`googlezip`・`google-proxy`)はHTMLだけ取りに来るので「ビーコンなし」になり、実訪問には数えない
   - **再訪(前日以前にも来た人)**(2026-10-15追加)。ビーコンの送信元ごとに、2つの目印を出す。どちらか一方でも当たれば再訪の候補。
     - 「目印」: ビーコンに`r=1`が付いた件数。ブラウザが初めて来た日時をlocalStorage(`visitHistory`)に覚えていて、30分以上あいて始まった訪問が初めて来た日より後の日なら付ける。IPが変わっても分かるが、Xアプリ内のブラウザとSafariのように保存領域が別になると分からない。10/15より前のビーコンには付いていない
     - 「前の来訪」: 同じIPから前日以前にビーコンが来ていた日(日本時間、直近5日分まで)。ログが残る約5週間分だけ見る。携帯回線やVPNはIPが変わるので取りこぼす
     - 同じプレイヤーを開いている・お気に入り画面をいきなり開いた、などスクリプトで拾えない手がかりは、メモと照らして判断する(9/29→9/30のドコモの人はIPが変わったが、同じプレイヤーを毎日開いていたので再訪と分かった)
   - **ボット込みの総リクエスト**(2026-10-22追加)。除外する前の全リクエスト数・ユニークIP数、HTMLページの表示数(GETで200。静的ファイル・ビーコン・robots.txt・sitemapは除く)、ボット別のリクエスト数。**毎回の報告に「おまけ」として必ず載せる**(2026-10-22にユーザーが依頼)。実訪問の数には関係しない。サーバーの負荷や、新しいクローラーが現れたこと(10/22にShapBotが8時間で約11万件)に気づくための参考値

2. 「日次集計」「既知のノイズ除外後」の数字はログの行数で、クローラーが大半を占める参考値。
   これを「実アクセス」として報告すると、スキャナーを実訪問者として数えてしまい
   実態より楽観的な報告になる(2026-09-20に実際にこの間違いをした)。実訪問はビーコン(次の2.5)で数える。
   - ビーコンの送信元には逆引き結果が出るので、報告ではそれを見て「どこの誰らしいか」まで添える
     (例: `eonet.ne.jp`なら関西の固定回線=実訪問者の可能性が高い)。データセンター判定の基準は
     `references/known_noise.md`の「データセンター由来の一括除外」を参照。

2.5. **ビーコン(`/beacon`)の数字が出ていれば、それを最も確かな指標として扱う**(2026-09-22導入、
   `archive/進捗ログ_2026-09.md`のフェーズ1.61)。ビーコンはブラウザがJSを実行したときだけ叩かれるため、
   HTMLを取得するだけのクローラーは現れない。ログのUA/IPからの推定と食い違ったら
   ビーコン側を信じる。ただしJSを切っている閲覧者は数えられないので、ビーコンの数は
   実訪問の下限として読む。
   - 2026-09-30に送信のタイミングを`load`から`DOMContentLoaded`に早めた(フェーズ1.101)。それまでは
     iPhoneのXアプリから来た人の約2割(27人中6人)で、HTMLとCSSは取得したのにビーコンが来ていなかった。
     取りこぼしの割合は`scripts/beacon-miss-check.sh "<開始(UTC)>"`で確かめられる(X経由の訪問ごとに、
     同じIPから120秒以内にビーコンが来たかを突き合わせる)。変更後(9/30〜10/4)は8人中0人になったので、
     取りこぼしていたのは「すぐ閉じた人」だったとみている(人数が少ないので断定はしない)。

3. ビーコンの送信元でも、そのまま実訪問者と決めつけず、
   - 送信元がクラウド/データセンターのIP帯(Google `34.x`/`35.x`/`66.249.x`、AWS、DigitalOcean、Linode、Vultr等)でないか
   - 同じIPが短時間で全ページ種別を機械的に巡回していないか(スキャナーの典型パターン)
   を確認する。怪しければ「スキャナーの可能性が高い」と留保つきで報告し、断定はしない。

4. `references/known_noise.md`に載っていない新しいIPが「明らかに自動化された挙動」(例: `/.git/config`・クラウドのメタデータエンドポイントへの到達試行、全ページを秒単位で機械的に巡回)を示していたら、その場で`known_noise.md`に追記してよい。ただし「本当にユーザー本人のアクセスか」は紛らわしい場合があるので(2026-09-20に一度誤判定した経緯がある)、判断に迷うIPは除外せずユーザーに確認する。

5. ユーザー自身の開発用IP(`known_noise.md`参照)は固定でない可能性があるため(`CLAUDE.md`のAPIキー節を参照)、長時間・広範囲にサイトを巡回している単一IPを見つけたら、スキャナー断定の前に「これはご自身のアクセスですか?」と確認するのも有効。

6. **収録人数の表記の定期確認(週1回が目安、2026-09-23にユーザーが依頼)**。
   トップページの検索ボックスの下には「〇〇万人以上を収録」という固定の人数が出ている
   (`home.player.nameHint`の10言語分と、`SitemapController`の`/llms.txt`)。巡回で索引は増え続けるので、
   放っておくと実態より少ない数字のまま損をする(2026-09-23に「900万人以上」のまま実数が2100万人に達していた)。
   `references/indexed_count_check.md`の最終確認日から**7日以上たっていたら、報告の最後で確認をレコメンドする**
   (「前回の確認から◯日たっています。収録人数の表記を確認しますか?」)。ユーザーが了承したら、
   `crawler-status`スキルと同じく`by-tag`全ファイルの行数合計で実数を数え、表記とのずれを報告する。
   表記を変えるかどうかはユーザーに確認する。コードの変更になるので、作業はworktreeで行う。
   表記を変えたら、Xのプロフィール文(Bio)の人数も合わせて直す(2026-09-24に「9M+」のまま放置されていたのを直した。`宣伝戦略.md`の「Xの運用方針」)。
   確認したら、表記を変えなかった場合も`indexed_count_check.md`に1行追記する。

7. **日別ドキュメントに1行追記する(2026-09-26にユーザーが依頼)**。
   集計したら、Claude Docsのドキュメント「アクセス状況(日別)」
   (`https://claude.ai/code/artifact/07ff8c83-6635-4dcf-a087-058d5554133c`)の表にその日の行を足す。確認は不要。
   - 1行 = 日本時間の1日。新しい日を表の一番上(見出し行のすぐ下)に入れる。列は「日付 | 実訪問 | うち再訪 | PV | Xからの流入 | 検索から | メモ」の7列(人間候補の列は消してある。8つのセルで行を足すと`shape_mismatch`で拒否される)。
   - **実訪問**: ビーコンの送信元のうち、データセンター・クラウド由来(`*`付き、逆引きなしでもAlibaba等と分かるもの)を除いた人数。人かどうか判断できないものは「1(不明)」のように書く。
   - **うち再訪**: 実訪問のうち、前日以前にも来たことがある人数(2026-10-15に列を追加し、9/22以降の行もIPの一致とメモの記録からさかのぼって埋めた)。出力の「再訪」の目印か前の来訪のどちらかがある人に、メモから分かる人を足す。同じ日に何度も来た人は数えない。メモに「10/13以来2日ぶり」のように書く。
   - **PV**: 実訪問に数えた送信元のビーコン件数の合計(ビーコンはページ表示1回につき1件)。出力の「送信元IP別」の件数を足す。実訪問で「不明」とした送信元の分は「7+1(不明)」のように分けて書く(2026-09-29にユーザーが依頼)。
   - **Xからの流入**: 出力の「X(from=x・xreply)の人数」(ビーコンで確かめたX経由の人数。データセンター由来を除く)。10/22の行からこの定義で、それより前の行は人間候補の`?from=x`と`?from=xreply`のリクエスト件数(すぐ閉じた人や同じ人の二重取得も数えていた)。
   - **検索から**: 「検索エンジン経由の訪問」の「実訪問」の人数(2026-10-04に列を追加し、ビーコン導入後の9/22以降の行もさかのぼって埋めた)。
   - **メモ**: 実訪問者の回線とどのページを見たか、など一言。
   - 日の途中で集計したときは日付に「※HH:MMまで」を付ける。次に集計したとき、その行を1日分の数字で置き換える。
   - 前回の行から日が空いていたら、スクリプトに日付を渡して(`check-access.sh 2026-09-25`のように)抜けた日も集計して埋める。
   - ドキュメントの操作はdocsスキル(`anthropic-skills:docs`)を読み込んでから行う。
   - 更新したら、ドキュメントをユーザーの画面に開く。確認は不要(2026-09-28にユーザーが依頼)。開くときはPowerShellの`Start-Process chrome "https://claude.ai/code/artifact/07ff8c83-6635-4dcf-a087-058d5554133c"`を使う(2026-10-13から。Artifactツールの`open`では画面に表示されないことがあった)。

8. **グラフ(「アクセス推移グラフ」)のデータも差し替え、日別ドキュメントと両方を開く(2026-10-31にユーザーが依頼)**。
   主要指標(実訪問・うち再訪・PV・Xからの流入・検索から)の日別グラフを、Dashboardの型のArtifact(`https://claude.ai/artifact/ForKbCRDkW7A6SoWZNwyL9`)に置いている。直近7日の1日平均と前の7日との比較、実訪問の7日移動平均も出す。確認は不要。
   - 元データは`history/daily.csv`(このスキルのフォルダ。列は`date,visitors,visitors_unknown,revisits,pv,pv_unknown,x,search,partial_until`)。日別ドキュメントの表と同じ値を、1行=日本時間の1日で古い順に書く。「22+1(不明)」は`visitors`=22・`visitors_unknown`=1のように分け、日の途中の集計は`partial_until`に「16:34」のように時刻を入れる(グラフで薄く出し、平均には入れない)。1日分で置き換えたら空にする。
   - 差し替え方: ①CSVを直す ②Artifactツールで`url`=上のURL・`file_path`=CSV・`asset: true`でアップロードする(`.tsv`は受け付けない) ③ArtifactDataで`datasets/daily`を読み、返ってきた`version`を`if_version`に付けて`update`し、`source.url`をアップロード結果の`/_blob/<id>`に、`updated.at`を今のUTCの時刻にする ④古いファイルはArtifactツールの`action: "delete"`(`url`と`path`=古いid)で消す
   - 両方をユーザーの画面に開く: `Start-Process chrome "https://claude.ai/code/artifact/07ff8c83-6635-4dcf-a087-058d5554133c"; Start-Process chrome "https://claude.ai/artifact/ForKbCRDkW7A6SoWZNwyL9"`
   - CSVは記録として、masterに直接コミットしてよい(`ranking-live`の`history/players.tsv`と同じ扱い)

## 報告フォーマット

以下の形式でまとめる(数字は毎回変わるので都度取得すること、過去の値を使い回さない)。

```
## アクセス状況(<日付>、UTC <開始>〜<終了>時点=日本時間 <開始>〜<終了>)

| 実訪問 | うち再訪 | PV | Xからの流入 | 検索から |
|---|---|---|---|---|
| N人 | N人 | N | N人 | N人 |

- **実ブラウザ表示(ビーコン): N件 / ユニークN IP**(データセンター由来を除いた実訪問の数え方も添える)
- <実訪問者の回線(逆引き)と、どのページを見たか>
- <再訪の人数と、前回いつ来た人か>
- <X経由の流入。ビーコンの「流入元タグ別」の人数と、`?from=x`・`?from=xreply`の内訳>
- <検索エンジン経由の実訪問の人数と、どのページに入ってきたか>
- 参考: 日次集計 N件 / N IP、既知のノイズ除外後 N件 / N IP(クローラーが大半)

### おまけ: ボット込みの総リクエスト
- 全リクエスト N件 / ユニークN IP、HTMLページの表示 N件
- <ボット別の上位と、前回は見なかったボットが出ていればその名前>
```

前回セッションでの数値と比較できると良いが、正確な比較には毎回このスクリプトで取り直した最新の値を使う。
